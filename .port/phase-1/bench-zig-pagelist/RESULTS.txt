[MEASURED] UNDERLYING PAGE-ALLOCATOR SYSCALLS (mmap count) — arena replay (--arena-sim)
--------------------------------------------------------------------------------
NOTE: dtruss/fs_usage require root (SIP) and non-interactive sudo is unavailable here,
so direct mmap-syscall tracing of the live binary was INFEASIBLE. Instead this is
MEASURED by replaying the exact std-page item allocation sequence through a REAL
std.heap.ArenaAllocator over the REAL std.heap.page_allocator, wrapped in a counting
allocator (identical mechanics to PagePool's arena). Faithful, just isolated.

  items=4  (init preheat path)        -> underlying page allocs = 2 ; bytes = 3,182,736
  items=8                              -> underlying page allocs = 3 ; bytes = 7,502,136
  items=9  (workload live peak)        -> underlying page allocs = 3 ; bytes = 7,502,136
  items=13                             -> underlying page allocs = 4 ; bytes = 14,890,572

  => The arena's 1.5x geometric growth amortizes mmaps: backing page-allocator
     allocations are O(log(items)). For this workload the main PagePool needs
     ~3 underlying mmaps (to back up to 9 std pages); arena_resize on the page
     allocator always FAILS (each growth = a fresh mmap node), so growth count =
     number of geometric arena nodes, not number of pages.

--------------------------------------------------------------------------------
[DERIVED-from-code] LAZY-ZERO / mmap characteristics
--------------------------------------------------------------------------------
  - pageAllocator() on Darwin = mach.taggedPageAllocator(.application_specific_1):
    mmap(MAP_ANON) tagged memory => kernel-zeroed lazily (zero-fill-on-demand);
    pages are not physically backed until first touch (matches low page-faults=0
    and reclaim-driven footprint above).
  - std page = 589824 B is a multiple of 16 KiB (asserted: total_size % page_size_min == 0),
    so every std page is exactly 36 hardware pages.
  - MemoryPool preheats 4 std pages at init (page_preheat=4) => init reserves
    4*589824 = 2,359,296 B of pool capacity even though only 1 page is used.
  - reset() uses retain_with_limit = page_count*item_size, so the pool keeps backing
    for ceil(rows/cap.rows) pages (1 page for 24 rows) and does NOT munmap on reset.
