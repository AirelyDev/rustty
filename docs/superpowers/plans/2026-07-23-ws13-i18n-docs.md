**Architecture:** i18n has three layers and WS13 touches all three. **Layer 1 — catalogs (DONE, do not redo):** `po/` holds 31 rebranded `.po` catalogs + `po/io.airely.rustty.pot`; `xtask/src/res_misc.rs:352-402` (`gen_locale`) compiles them with Homebrew/system `msgfmt` into `zig-out/share/locale/<locale>/LC_MESSAGES/io.airely.rustty.mo`, mirroring `GhosttyI18n.zig:33-43`, and the macOS Xcode Copy-Resources phase ships that tree (`macos/Rustty.xcodeproj/project.pbxproj:81`). **Layer 2 — runtime binding (DONE):** `rustty_os::locale::ensureLocale` sets `LANG` from Cocoa preferences on macOS (`locale.rs:44-50`), then `rustty_os::i18n::init` binds the domain to `<share>/locale` (`i18n.rs:59-97`) and the GTK `Application` calls `initGlobalDomain` → `textdomain(BUNDLE_ID)` (`application.rs:2099`). **Layer 3 — call sites (THE GAP):** the `.blp` templates carry `_("…")` (51 unique msgids, translated by GtkBuilder through the global domain) but three of them still spell "Ghostty"; the 25 Rust-side literals the oracle wraps in `i18n._()` are plain untranslated string literals; and `rustty_translate` (`crates/rustty-apprt-c/src/lib.rs:1031`) returns `msgid` unchanged. ## De-risking findings (empirical, run at plan-authoring time)

Every number below was measured, not assumed. Probe scripts are throwaway (under `$CLAUDE_JOB_DIR/tmp`); the plan re-derives each fact with a committed test.

**F1 — The catalogs work. Proven end-to-end with rustty's OWN vendored libintl.** A C probe linked against `target/debug/build/gettext-sys-*/out/librustty_intl.a` (WS9's archive, plus `-liconv -framework CoreFoundation`, and **no Homebrew libintl on the link line**), pointed at a `share/locale` tree built by `msgfmt` from `po/de.po`:

```
setlocale -> de_DE.UTF-8
bindtextdomain -> …/loc
hit  : Über Rustty          # dgettext("io.airely.rustty", "About Rustty")
stale: About Ghostty        # dgettext(…, "About Ghostty")  → passthrough
absent: not a real msgid at all
RESULT translate=YES stale_passthrough=YES
```

**F2 — …but only when the locale comes from the ENVIRONMENT.** The same probe with `setlocale(LC_ALL, "de_DE.UTF-8")` called in-process and **no** `LC_*`/`LANG` in the environment printed `hit : About Rustty` — i.e. `translate=NO`. `LANGUAGE=de` alone also failed. Only `LC_ALL=de_DE.UTF-8` / `LANG=de_DE.UTF-8` **in `env`** produced a translation. This dictates the shape of T5's test: it must spawn a child process with the env set, not call `setlocale` inside the test (which would also require `unsafe { std::env::set_var }` under edition 2024). It also confirms why `rustty_os::locale::ensureLocale`'s macOS `setLangFromCocoa()` (`locale.rs:44-50`) is load-bearing for a Finder-launched app — it puts `LANG` in the environment before `i18n::init` runs.

**F3 — Exactly 3 `.blp` msgids can never match a catalog.** Extracting all `_("…")` from `crates/rustty-apprt/assets/ui/**` yields **51 unique msgids**; the `.pot` holds **75**; the set difference (blp − pot) is exactly:

```
crates/rustty-apprt/assets/ui/1.3/debug-warning.blp:6   ⚠️ You're running a debug build of Ghostty! Performance will be degraded.
crates/rustty-apprt/assets/ui/1.5/inspector-window.blp:5  Ghostty: Terminal Inspector
crates/rustty-apprt/assets/ui/1.5/window.blp:307         About Ghostty
```

and the catalogs carry the Rustty spellings of all three (`po/io.airely.rustty.pot:82,86,239`; `po/de.po:89-92,95-96,251-252`). A Python `gettext` lookup against the compiled `de` catalog confirms the consequence: `'About Rustty' → 'Über Rustty'` but `'About Ghostty' → 'About Ghostty'`. So today a German user sees an **untranslated, wrongly-branded** menu item. Also non-translatable but wrongly branded: `assets/ui/1.4/clipboard-confirmation-dialog.blp:14` `body: "If you see this text, there is a bug in Ghostty. Please report it."`.

**F4 — Zero code-side msgids are wrapped.** Running `xgettext --language=C --keyword=_ --keyword=gettext_ --keyword=C_:1c,2` over all 67 `.rs`+`.blp` files of `crates/rustty-apprt/{src,assets}` extracted **52 msgids, none from a `.rs` file** (`grep -n '\.rs:' all.pot` → no hits). The `.pot`'s remaining 25 entries are precisely the ones whose oracle refs are `*.zig:` — the code-side set. 23 of the 25 were located as plain literals in the port (exact file:line table in T3); the other two are the About dialog's, one of which the port composes with `format!()` (`class/window.rs:1870`) — see T3 Step 4.

**F5 — `xgettext --language=C` handles Rust well enough, and `--keyword=gettext_` works.** A probe file containing `i18n::gettext_(c"Copy")`, `gettext_(c"About Rustty")` and `i18n::gettext_("Paste")` extracted all of them (the C lexer tokenizes `i18n::gettext_` such that the `gettext_` keyword matches, and the `c"…"` prefix is harmless). Over the real tree it exits `rc=0` with **180 `warning: unterminated character constant`** lines — Rust lifetimes (`'a`) seen as char literals. Non-fatal, but it means extraction completeness cannot be assumed: T1's committed coverage test, not xgettext, is the authority on "every msgid is present".

Fedora VM: `groff` YES, `mandoc` NO, `pandoc` NO. `de_DE.UTF-8` exists on both (macOS `locale -a` lists `de_DE.UTF-8`; the VM lists `de_DE.utf8`). **`pandoc` exists nowhere**, so the oracle's `pandoc --to man` / `--to html` steps (`GhosttyDocs.zig:60-88`) cannot be shelled out to.
```rust
//! I18N MSGID COVERAGE — the gate that makes "translations ship" falsifiable.
//!
//! A gettext msgid is a LOOKUP KEY. If a runtime call site spells a msgid even
//! one byte differently from the committed catalogs, gettext silently returns the
//! msgid unchanged and the string is permanently untranslatable — no crash, no
//! warning, no failing build. That is exactly the state WS13 found: three `.blp`
//! msgids still said "Ghostty" while all 31 catalogs said "Rustty".
//!
//! These tests read the SAME files the build and the runtime read, and assert the
//! msgid sets agree in both directions:
//!
//!   * every `_("…")` in `assets/ui/**/*.blp` exists as a msgid in the `.pot`;
//!   * every `gettext_(c"…")` in `src/gtk/**/*.rs` exists as a msgid in the `.pot`;
//!   * every `.pot` msgid whose reference comment cites a code file (`*.zig:`,
//!     i.e. the oracle's code-side set) is actually wrapped somewhere in
//!     `src/gtk/**/*.rs` — this is the half that catches an UNWRAPPED literal,
//!     which a one-directional check would miss entirely.
//!
//! Deliberately NOT feature-gated and pure `std`: it must run on macOS (where the
//! `gtk` feature does not build) as well as on Linux, since the `.blp` assets and
//! the catalogs are platform-independent data.
#![allow(clippy::needless_raw_string_hashes)]

use std::collections::{BTreeMap, BTreeSet};
use std::path::{Path, PathBuf};

fn repo_root() -> PathBuf {
    Path::new(env!("CARGO_MANIFEST_DIR"))
        .join("../..")
        .canonicalize()
        .expect("workspace root")
}

/// Parse a `.po`/`.pot` byte stream into `msgid -> the reference comment block`.
/// Handles gettext's multi-line string continuation (`msgid ""` followed by
/// `"…"` lines) and C escapes for `\"` and `\n`, which is all the corpus uses.
fn parse_pot(bytes: &[u8]) -> BTreeMap<String, String> { /* …implementation… */ }

/// All `_("…")` msgids in the blueprint templates, with `file:line` provenance.
fn blp_msgids(root: &Path) -> BTreeMap<String, String> { /* …implementation… */ }

/// All `gettext_(c"…")` msgids in the GTK Rust sources, with `file:line`.
fn code_msgids(root: &Path) -> BTreeMap<String, String> { /* …implementation… */ }

#[test]
fn blp_msgids_all_exist_in_pot() {
    let root = repo_root();
    let pot = parse_pot(&std::fs::read(root.join("po/io.airely.rustty.pot")).unwrap());
    let blp = blp_msgids(&root);
    assert!(blp.len() >= 51, "expected >=51 blueprint msgids, found {}", blp.len());
    let missing: Vec<_> = blp
        .iter()
        .filter(|(m, _)| !pot.contains_key(*m))
        .map(|(m, where_)| format!("{where_}: {m:?}"))
        .collect();
    assert!(
        missing.is_empty(),
        "these blueprint msgids exist in no catalog, so they can NEVER translate \
         (fix the .blp to match the catalogs — the catalogs are authoritative, R2):\n{}",
        missing.join("\n")
    );
}

#[test]
fn code_msgids_all_wrapped_and_in_pot() {
    let root = repo_root();
    let pot = parse_pot(&std::fs::read(root.join("po/io.airely.rustty.pot")).unwrap());
    let code = code_msgids(&root);

    // Direction 1: nothing wrapped in code may be absent from the catalogs.
    let unknown: Vec<_> = code
        .iter()
        .filter(|(m, _)| !pot.contains_key(*m))
        .map(|(m, w)| format!("{w}: {m:?}"))
        .collect();
    assert!(unknown.is_empty(), "wrapped msgids absent from the catalogs:\n{}", unknown.join("\n"));

    // Direction 2 (the one that catches an unwrapped literal): every catalog entry
    // the ORACLE sources from code (`*.zig:` reference comment) must be wrapped here.
    let expected: BTreeSet<&String> = pot
        .iter()
        .filter(|(_, refs)| refs.contains(".zig:"))
        .map(|(m, _)| m)
        .collect();
    assert!(expected.len() >= 25, "expected >=25 code-side catalog msgids, got {}", expected.len());
    let unwrapped: Vec<_> = expected
        .iter()
        .filter(|m| !code.contains_key(**m))
        .map(|m| (*m).clone())
        .collect();
    assert!(
        unwrapped.is_empty(),
        "these msgids are translated in all 31 catalogs but no Rust call site looks \
         them up — they are shipped as untranslated English literals:\n{unwrapped:#?}"
    );
}
```

```rust
///
/// Translate a string maintained by librustty into the current
/// application language. This will return the same string (same pointer)
/// if no translation is found, so the pointer must be stable through
/// the function call.
///
/// This should only be used for singular strings maintained by Rustty.
//
// pub export fn ghostty_translate(msgid: [*:0]const u8) [*:0]const u8 {
//     return internal_os.i18n._(msgid);
// }
//
// PORT NOTE (WS13): this used to return `msgid` unchanged. The two reasons the old
// note gave are both resolved: (1) `_dgettext` IS now defined by rustty's own
// vendored libintl (`crates-sys/gettext-sys` -> `librustty_intl.a`, WS9 `9af41cc`),
// so linking `gettext_` no longer fails; (2) `i18n.init`'s `bindtextdomain` IS
// called during app bootstrap (`rustty-apprt/src/lib.rs:322`, WS4). So this now
// forwards for real, exactly as `main_c.zig:150-152` does. The "same pointer if no
// translation is found" contract is gettext's own behavior, preserved verbatim.
//

// `CString::new(BUNDLE_ID)` and one `dgettext` call; the `CString` cannot fail on a
// compile-time constant with no interior NUL, and `dgettext` never panics. There is
// therefore no panic edge to catch here, and no `catch_unwind` is added (adding one
// would be the only alternative).
///
/// # Safety
/// `msgid` must be a valid NUL-terminated C string that stays valid through the call.
#[no_mangle]
pub unsafe extern "C" fn rustty_translate(msgid: *const c_char) -> *const c_char {
    // return internal_os.i18n._(msgid);
    let msgid_c = unsafe { std::ffi::CStr::from_ptr(msgid) };
    rustty_os::i18n::gettext_(msgid_c).as_ptr()
}
```

- Produces: `pub fn markdown_to_roff(md: &[u8], section: u8) -> Vec<u8>` and `pub fn markdown_to_html(md: &[u8]) -> Vec<u8>`; installed artifacts `share/man/man1/{APP}.1`, `share/man/man5/{APP}.5`, `share/{APP}/doc/{APP}.{1,5}.md`, `share/{APP}/doc/{APP}.{1,5}.html`.

**Decision — why a Rust renderer instead of `pandoc` (state this in the module doc):** the oracle shells out to `pandoc --to man` / `--to html` (`GhosttyDocs.zig:60-88`). F6 measured that `pandoc` is absent on BOTH the macOS host and the Fedora VM. Three options were weighed. (a) _Require pandoc_: matches the oracle exactly, but adds a heavyweight host build dependency that neither platform has, and would make `xtask resources` — a step every packaging run needs — fail on a stock machine. WS9 deliberately went the other way, vendoring rather than depending. (b) _Emit roff directly from `mdgen`, skipping markdown_: fewer moving parts, but it discards the `.md` and `.html` artifacts the oracle installs into `share/ghostty/doc/`, and it makes the generator's output un-diffable against the oracle's markdown. (c) _Generate the oracle's markdown verbatim, then convert in Rust_: keeps `mdgen`'s output byte-comparable to the oracle's (modulo R2), produces all three installed formats, adds no host dependency, and the conversion is unit-testable. **(c) is chosen.** The markdown subset that must be supported is small and closed, because `mdgen` is the only producer: the `%`-title block, `#`/`##` headings, blank-line paragraphs, pandoc definition lists (`term` then `:   def`), `**bold**` / `_italic_` / `` `code` ``, `-` bullets, 4-space indented code blocks, `<url>` autolinks and `[text](url)` links.

## Deviations from the plan as written, and why

1. **T3 wraps the code-side strings through a new `gtk::i18n::tr` helper**
   (`crates/rustty-apprt/src/gtk/i18n.rs`) rather than repeating
   `rustty_os::i18n::gettext_(…).to_str().unwrap_or(…)` at 24 sites.
   `gettext_` returns `&'static CStr` and every gtk-rs setter wants `&str`, so
   the plan's inline pattern would have been copied verbatim two dozen times.
   `xtask update-translations` gained `--keyword=tr` alongside
   `--keyword=gettext_` so extraction is unaffected.
2. **The config-field count is 204, not the plan's 183**, and the `.pot` counts
   moved with the tree since plan-authoring. The tests pin the live numbers so a
   silently-shrinking table cannot make a per-field loop vacuous.
3. **`markdown_to_roff` takes no `section` parameter.** The `%`-title block is
   the single source of truth for both the page name and its section; a separate
   argument would create two sources that can disagree. A `title` OVERRIDE does
   exist, for the `identity-oracle` profile (F7's bug).
4. **The `.TH` date field is populated** from a committed constant. pandoc
   leaves it empty, which makes `mandoc -Tlint` warn on every generated page —
   a gate that can never go green. A constant, not a clock read, keeps the
   output byte-reproducible.
5. **`main_build_data` landed as an `xtask` SUBCOMMAND, not a second binary**
   (`xtask gen +<action>`). The reference splits it out only to stop `build.zig`
   rebuilding when its data dependencies change — a Zig build-graph concern
   cargo does not have — and `xtask` is the only crate already depending on both
   `rustty-extra` and `rustty-terminfo`.
6. **The plan's T7 Step 5 expected `new_split` in `rustty.1`.** It is in
   `rustty.5`: `main_ghostty_1.zig` assembles ACTIONS + CONFIG, and
   `main_ghostty_5.zig` assembles CONFIG + KEYBIND ACTIONS. The port follows the
   reference; the plan's expectation was wrong.
7. **V5 → V7.** The RTL row is `VERIFICATION_DEBT.md` **V7**, not V5 (V5 and V6
   were taken by WS16/WS19 after this plan was written), and it is owned by
   **Phase 3** rather than WS13 — see the row for the reasoning.
8. **The live headed GTK screenshot steps (T2 Step 6, T3 Step 6) were not run.**
   Their assertion is subsumed by two mechanical gates that did run and that
   carry the same negative controls: `i18n_msgid_coverage` (the msgid a widget
   will look up EXISTS in the catalogs, both directions) and `i18n_translate`
   (the lookup itself returns the German/Japanese `msgstr` and falls through
   under `LANG=C`). What a screenshot would add over those is the widget-render
   leg, which is the same human-visual leg V7 ledgers. Recorded as I.1/I.2 in
   `docs/manual-test-plan-gtk.md`.
