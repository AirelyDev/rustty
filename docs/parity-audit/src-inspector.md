### Medium severity

#### S108-F1 — modesTable omits `report_visibility` (?2033) and `kitty_paste_events` (?5522) rows

- **Status:** ✅ CONFIRMED (both verifier lenses failed to refute)
- **Kind:** missing-branch
- **Severity:** medium (corrected: medium)
- **Oracle:** `src/inspector/widgets/terminal.zig:591-616`
- **Rustty:** `crates/rustty-inspector/src/widgets/terminal.rs:1220-1270, 1330`

**Description.** The oracle's `modesTable` iterates every field of `terminal.Mode` via `inline for (@typeInfo(terminal.Mode).@"enum".fields)`, so it renders one checkbox/number/name row per mode, including `report_visibility` (value 2033, `modes.zig:330`) and `kitty_paste_events` (value 5522, `modes.zig:336-341`). The Rust port hand-expands this comptime loop into the `MODES: &[(Mode, &CStr)]` table, which stops at `Mode::ReportColorScheme` → `Mode::InBandSizeReports` and never lists `Mode::ReportVisibility` or `Mode::KittyPasteEvents`, even though both variants exist in rustty-vt (`crates/rustty-vt/src/modes.rs:320, 322`) and `t.modes.get()` supports them. Consequence: the inspector's Terminal Modes table shows 40 rows instead of 42; a user inspecting a program that sets DECSET 2033 or 5522 sees no row for it. Row ordering is also affected (`report_visibility` should appear between `report_color_scheme` and `in_band_size_reports`).

**Evidence.** Oracle `modes.zig` entries list (grep `.name =`) contains `report_visibility` (line 330) and `kitty_paste_events` (line 337); rustty `modes.rs` has `ReportVisibility = 2033` (line 320) and `KittyPasteEvents = 5522` (line 322); `grep -n 'Mode::ReportVisibility\|Mode::KittyPasteEvents' crates/rustty-inspector/src/widgets/terminal.rs` returns nothing; the MODES table at `terminal.rs:1220-1270` ends `(Mode::ReportColorScheme, c"report_color_scheme"), (Mode::InBandSizeReports, c"in_band_size_reports")`.

Both lenses independently confirmed that the oracle's generated `Mode` enum includes all `entries` regardless of `.disabled` (the `!entry.disabled` guard lives only in `modeFromInt`, `modes.zig:179-186`), so both modes really are rendered upstream. A relocation search across `crates/`, `crates-sys/`, `include/`, `macos/`, `xtask/` found zero `report_visibility`/`kitty_paste_events` hits anywhere in `rustty-inspector`, and no PORT NOTE claims a deferral — the only PORT NOTE (`terminal.rs:1209-1219`) asserts the table is "in exact declaration order", which makes the omissions drift rather than a deliberate difference.

**Suggested fix.** Insert `(Mode::ReportVisibility, c"report_visibility")` between the ReportColorScheme and InBandSizeReports rows, and append `(Mode::KittyPasteEvents, c"kitty_paste_events")` after InBandSizeReports, so MODES matches the `Mode` enum's declaration order exactly (ideally derive the table from a single canonical list shared with `modes.rs` so future mode additions cannot drift).

#### S109-F1 — `pub fn eventTable(events)` has no rustty counterpart

- **Status:** ⚠️ DISPUTED (the semantic lens refuted; the presence lens confirmed)
- **Kind:** missing-function
- **Severity:** low (corrected: low)
- **Oracle:** `src/inspector/widgets/termio.zig:435-473`
- **Rustty:** `crates/rustty-inspector/src/widgets/termio.rs:303-310`

**Description.** The oracle defines `pub fn eventTable(events: *const VTEvent.Ring) void` (a 3-column Seq/Kind/Description ImGui table over the ring in reverse order, returning early if `BeginTable` fails). rustty only carries the commented-out `// eventTable(events);` TODO call site inside `draw` (`termio.rs:308-309`) and never defines the function (grep for `eventTable`/`event_table` in `crates/rustty-inspector` finds only those comments). In the oracle the function is dead code (its only call is commented out at `termio.zig:119-120`), so there is no runtime behaviour change, but the pub API surface is not fully ported.

**Evidence.** `termio.zig:435 pub fn eventTable(events: *const VTEvent.Ring) void {` … `:473`; `termio.rs:303-310` contains only the `// TODO: Eventually // eventTable(events);` comment; no `fn eventTable`/`event_table` anywhere in `crates/rustty-inspector/src`.

**Suggested fix.** Add a `pub fn event_table(events: &VTEventRing)` mirroring `termio.zig:435-473` (BeginTable `"events"` `RowBg|Borders` with early return, three `TableSetupColumn` calls, reverse-iterate rows with PushIDPtr/PopID, SameLine, `%d` seq, `%s` kind, `%s` raw_description).

**Refuting lens — semantic (confidence: high), verbatim:**

> Verified both sides: ghostty/src/inspector/widgets/termio.zig:435-473 defines `pub fn eventTable`, and grep for `eventTable` in that file (and src/inspector/*.zig) returns exactly two hits: the definition at :435 and the COMMENTED-OUT call at :120 (`// eventTable(events);` inside the `else` branch of the `events.empty()` check at :116-121). rustty crates/rustty-inspector/src/widgets/termio.rs:303-310 reproduces that branch faithfully, including the same `// TODO: Eventually // eventTable(events);` comment, and the `Waiting for events...` arm matches. The function is unreachable dead code in the oracle, so no input or state can produce a different observable result; per the lens, a difference confined to unreachable code is refuted. (If the oracle ever uncomments the call, this becomes a real gap, but at pin 20abdb50a it is not observable.)

**Non-refuting lens — presence (confidence: high):** verified the function is genuinely absent workspace-wide (only the two comment lines in `termio.rs:304, :309`), with no relocated port and no PORT NOTE citing it; confirmed low severity because the oracle's sole call site is itself commented out.
